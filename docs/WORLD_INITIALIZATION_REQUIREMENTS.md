# 世界与新游戏初始化需求

## 1. 目标

在开始 AP 规则迁移前，建立基本的世界初始化和游戏实例封装能力：应用读取并校验静态世界定义，构造类型明确的本局世界状态，并将其放入可保存的 `GameInstance`。本阶段不负责角色建卡或 AP 规则状态；回放不在范围内。

首个目标世界为旧 skill 中的 `isekai_grey`。初期实现服务于单人模块化单体，不要求账号体系、网络协作、分布式锁或通用规则 DSL。

## 2. 依据与兼容原则

- 玩家可见行为以旧 skill 为基线，重点核对 `SKILL.md` 开局章节、`scripts/persistence.py` 的 `cmd_init`、`scripts/lore_loader.py` 和 `world/isekai_grey/world_lore.json`。
- DiceFrame 仅作为架构参考：静态世界定义与运行时世界事实分离；新局创建由应用服务编排；内容物化须可校验、可重试，不重复应用。
- 保留 Python 的数值、默认值、难度影响、初始资源和选择语义。若确认要改变玩家可见行为，先在 `docs/MIGRATION_DECISIONS.md` 记录 before/after、理由、测试和影响。
- 不能只依据 README 摘要实现。迁移每个字段前都要对照当前 Python 源码和实际模板，并记录字段来源及转换规则。

## 3. 术语和数据所有权

### 3.1 World Definition（静态世界定义）

随应用分发或由内容目录管理的只读模板，例如世界名称和设定、区域、物种/怪物/NPC 类型、能力与物品模板、难度预设、任务和事件模板、出身场景池。该定义有稳定 `worldId` 和 `contentVersion`。加载后不得被某一局游戏的修改覆盖。

### 3.2 WorldState（本局动态世界状态）

一局游戏中的权威世界事实，例如游戏内日期与时刻、天气、季节、具体地点和通用区域、主线、威胁级别和计数、期限/随机事件、价格修正、剧情阶段、开场场景。它拥有自己的 revision，并与静态模板分开建模。

### 3.3 GameInstance（游戏实例）

当前 `GameInstance` 已包含游戏 ID、世界与内容版本、规则集 ID/版本、生命周期、revision 和 `WorldState`；规则集状态槽位暂为空，待 AP 迁移时填充。

### 3.4 规则集状态

职业属性、生命/行动资源、初始能力、等级、背包、专属天赋等规则专属权威数据由所选规则集拥有。它们不属于本阶段的世界初始化范围，后续 AP 迁移再定义其初始化方式。

## 4. 输入与前置校验

初始化世界的输入至少包括：

- `worldId`；首阶段支持 `isekai_grey`。
- 可选世界名称、描述、地点、区域、天气、季节、时刻及主线覆盖字段；仅纳入旧 skill 初始化器实际支持且字段含义明确的项目。
- 可选开场/出身场景覆盖值；未提供时是否抽取模板场景，按旧 skill 行为审计结果决定。

开始初始化前必须校验：

- 世界定义存在且受当前内容版本支持。
- 输入文本满足必要长度限制；具体限制按旧 skill 语义核实。
- 自定义出身场景按 Python 的既有语义处理；不能误当成模板 ID。
- 所需内容字段完整且结构正确，无法读取/解析时返回可诊断错误，不可静默降级成空世界。
## 5. 初始化流程

应用用例按以下顺序执行，具体类/API 名称由实现设计决定：

1. 解析请求并验证世界定义及世界初始化覆盖字段。
2. 记录本次运行采用的世界内容版本。
3. 从静态定义构建本局世界状态。按旧 skill 核对默认时间、地点、天气、季节、区域、威胁、剧情阶段和事件等字段，首版只实现审计后确认属于世界状态的字段。
4. 接受有效的开场/出身场景覆盖值；未提供时按审计确认的默认行为处理。
5. 返回类型明确的世界初始化结果。本阶段不创建角色/AP 状态，不调用存档适配器，也不调用 LLM。

## 6. 内容加载与版本

- `ContentCatalog` 应成为有明确查询和错误语义的端口/服务，而不是空标记接口。
- 世界模板来自受控内容根目录或 classpath 资源；禁止由 cwd、模块静态变量或全局活动存档推断路径。
- JSON 只承载静态数据；加载时验证 schema 版本、ID、一致性、必需字段、引用目标和集合边界。
- 内容定义加载后视为不可变值。初始化结果带有 `worldId`、`contentVersion`；持久化后的版本固定和快照策略留给存档读档需求。
- 机器判定枚举值保留稳定键；翻译只在展示层完成。
- 静态模板与本局可编辑实体名册/生成结果分开。旧 skill 的复制模板语义必须评估是否作为兼容要求；不得让某局的命名操作修改共享模板。

## 7. 持久化范围

当前已补充首版文件存档读档：使用带 `schemaVersion` 和 `gameId` 的 JSON 包装保存 `GameInstance`，写入采用临时文件加原子替换，读取会拒绝损坏或未知版本。当前实例中的角色/AP 规则状态槽位为空，后续 AP 迁移时填充；回放机制不在范围内。

## 8. API 与应用边界

- 提供应用层世界初始化用例，负责读取世界定义、校验输入、创建 WorldState 并返回只读摘要。
- API 控制器只负责请求解析和响应映射，不能依赖 `rulesets.ap` 的具体实现类或文件系统细节。
- HTTP 请求/响应 DTO 与领域对象分开；错误映射能区分输入无效和内容不存在/损坏。
- 当前已提供世界初始化、保存和读取的最小 HTTP 入口。
- 初始化结果至少标识世界 ID、内容版本、初始 revision 和面向 UI 的世界摘要，不直接暴露可变内部对象。

## 9. 建议模块职责

- `content`：世界定义模型、目录查询、JSON 解析和内容校验。
- `engine`：WorldState/GameInstance 生命周期与无规则集偏向的共享契约。
- `rulesets.ap`：本阶段不实现 AP 状态或初始化逻辑。
- `application`：世界初始化用例和内容版本固定。
- `application.port`：内容查询和完整游戏存储接口均由应用拥有。
- `persistence`：当前提供 WorldState 文件存储适配器和序列化版本处理。
- `api`：提供初始化、保存和读取的请求/响应 DTO、控制器和错误映射。
- `narrative`：本阶段不参与初始化；后续只消费确认后的投影和事件。

此模块拆分是建议的依赖方向，不要求为了满足名称而创建空壳类。实现应以可测试职责为准。

## 10. 测试要求

### 内容目录

- 能加载 `isekai_grey` 并校验必需字段和交叉引用。
- 缺文件、损坏 JSON、错误 schema、重复 ID、缺失必填字段和无效引用均产生确定错误。
- 世界内容被视作不可变；初始化或某局修改不能修改共享源模板。

### 初始化行为

- 为有效输入创建完整的 WorldState；检查必需字段、初始 revision、世界 ID 和内容版本。
- 非法世界、无效覆盖值和必填输入分别拒绝。
- 显式出身覆盖值有效时准确写入结果；未提供时从合法池中选择。
- 世界状态默认字段与 Python 源码及模板核对；本阶段不验证 AP 难度缩放和角色初始数值。

### 架构与 API

- `ArchitectureTest` 继续通过：engine/ruleset 不依赖 Spring、API、应用实现层、存储适配器。
- 应用层测试覆盖有效世界初始化、输入错误和缺失世界的错误语义。
